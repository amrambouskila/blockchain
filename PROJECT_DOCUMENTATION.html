Overview — what this is & why

A personal learning project for understanding Bitcoin internals by reading the reference implementation and re-implementing wallet mechanics in Python.

The goal of blockchain is to build a deep, hands-on understanding of how cryptocurrency works at the level of bytes and curve points — not to ship a product. The approach is to study the canonical Bitcoin Core C++ source as a reference and re-implement the wallet half from scratch in Python, so that every step from "256 random bits" to "a spendable Bitcoin address" is understood and owned. The authoritative statement of intent lives in docs/BLOCKCHAIN_MASTER_PLAN.md and the project rules in CLAUDE.md / AGENTS.md.

Today the project is a single Python module, bitcoin_wallet.py, containing one class, BitcoinWallet. It does the full cryptographic key-to-address derivation locally (random private key → compressed ECDSA public key → P2PKH Base58Check address) and then delegates all on-chain operations — balance, transaction construction, signing, broadcast — to a locally running Bitcoin Core node over JSON-RPC. The crypto is real; the chain interaction is real (against whatever node you point it at). What is not real is production-grade safety: see the warnings throughout this guide.

The project is explicitly phased (Phase 1: wallet basics → Phase 2: HD/BIP wallets, SegWit, multi-sig → Phase 3: a custom educational blockchain with PoW and P2P). Only Phase 1 has code, and even Phase 1 is mid-hardening: type annotations are present but docstrings, named constants, a pytest suite with test vectors, and edge-case handling are still on the to-do list per docs/status.md.

Do not
Never store real funds with this code. The entropy mixing, the lack of key encryption at rest, the plaintext private key in memory and in RPC calls, and the hard-coded fee all make this unsafe for mainnet value. It is a study tool. CLAUDE.md section 0 says this in the strongest terms.
Documentation drift — read this first
The project docs (CLAUDE.md, AGENTS.md, README.md, docs/status.md) describe a nested layout: blockchain_dev/bitcoin_wallet_dev/bitcoin_wallet.py for the wallet and blockchain_dev/bitcoin_blockchain_dev/ for a Bitcoin Core clone, plus a .claude/ directory. None of those exist on disk. The wallet actually lives at the repo root as bitcoin_wallet.py, there is no Bitcoin Core clone checked out (it is gitignored and absent), and the agent wiring is under .codex/ + .agents/, not .claude/. This guide documents the real on-disk state and flags the drift wherever it matters.

Architecture

A clean split: cryptography is done locally in Python; everything that touches the chain is delegated to a Bitcoin Core node over JSON-RPC.

There is exactly one process: your Python script. It holds the key material in memory and computes the address itself. For any operation that needs chain state — listing UTXOs, building/signing/broadcasting a transaction — it opens an HTTP JSON-RPC connection to a Bitcoin Core node (default 127.0.0.1:8332) and asks the node to do the work. The node, not this code, owns the mempool, the UTXO set, and the network.

The send flow (end to end)

The highest-level method, create_and_send_transaction(), chains five RPC-backed steps. The sequence below shows exactly who does what.

Key concept
The wallet derives its address from a public key it computes itself, but it asks Bitcoin Core to sign with the raw private key via signrawtransactionwithkey. The node never imports or stores the key; it is passed per call. That keeps the cryptographic ownership in Python while leveraging the node for serialization and consensus-correct signing.
Watch out — the reference half is not on disk
The architecture in docs/BLOCKCHAIN_MASTER_PLAN.md shows a "Bitcoin Core source (C++ reference, READ-ONLY)" component feeding study of the wallet. That clone is intended to live at blockchain_dev/bitcoin_blockchain_dev/ and is gitignored, but it is not currently checked out in this working tree. The READ-ONLY contract still applies the moment you clone it.

Core module — BitcoinWallet

One class does everything. Below, each method is broken out with its exact logic, inputs/outputs, and the security caveats that matter.

Entropy→Private key→Public key→Address→RPC ops
Constructor & wiring bitcoin_wallet.py:16-36

The constructor takes an optional RPC credentials filename and an optional private key (hex). It loads/creates credentials, opens the RPC connection, then either generates a fresh private key or uses the one provided. From the private key it eagerly derives the public key and address, so self.address is ready immediately after construction.

Watch out
The constructor connects to RPC before deriving keys. AuthServiceProxy is lazy (it does not actually connect until a method is called), so construction succeeds even with no node running — failures surface only when you call get_balance() or a tx method.
RPC credentials & connection bitcoin_wallet.py:38-60

get_rpc_credentials() loads rpc_credentials.json if present, otherwise generates a random rpc_user/rpc_password with secrets.token_hex and writes them to disk. connect_to_rpc() builds the URL http://user:pass@127.0.0.1:8332 and returns an AuthServiceProxy.

bitcoin_wallet.pyget_rpc_credentials (38-54), connect_to_rpc (56-60).
Watch out — credentials must match the node
Auto-generating credentials only works if your bitcoin.conf already trusts those exact user/password values. In practice you point the wallet at credentials your node already accepts (see Configuration). The auto-gen path is convenient for a first run but produces creds the node won't recognize unless you copy them into bitcoin.conf. The file is gitignored and blocked from AI edits by the pre-tool-use hook.
Private key generation bitcoin_wallet.py:62-66

Mixes three entropy sources and hashes them to a 256-bit value: secrets.token_bytes(32) (CSPRNG), os.urandom(32) (OS CSPRNG), and random.getrandbits(256) (the non-cryptographic Mersenne Twister). The concatenation is run through SHA-256 and returned as a 64-char hex string.

Key concept — why the mix is fine here but not in prod
Folding a weak source (random) into strong sources (secrets, os.urandom) via SHA-256 does not weaken the result — the output is as strong as the strongest input. CLAUDE.md calls the random mixing "acceptable for educational purposes but NOT acceptable in production." The cleaner production form is simply secrets.token_bytes(32).
Watch out — no curve-range check
A valid secp256k1 private key must be in [1, n-1] where n is the curve order. SHA-256 can theoretically produce 0 or a value ≥ n (probability negligibly small, but non-zero). The Phase 1 validation in .codex/commands/validate.md lists this range check as a requirement that the current code does not yet enforce.
Public key derivation bitcoin_wallet.py:68-92

Loads the 32-byte private key into ecdsa.SigningKey on the SECP256k1 curve, gets the verifying key, reads the public point's x and y integers, then builds the compressed public key: a 0x02 prefix if y is even, 0x03 if odd, followed by the 32-byte big-endian x. Result is a 33-byte (66 hex char) string.

Key concept — point compression
An secp256k1 point is (x, y), but for any x there are only two possible y values (one even, one odd) because the curve is symmetric about the x-axis. So you only need x plus one parity bit, encoded as the 02/03 prefix. That halves the key from 65 bytes (uncompressed, 04 prefix) to 33 bytes.
Address generation (P2PKH / Base58Check) bitcoin_wallet.py:94-104

The canonical Bitcoin "Hash160 + version byte + checksum + Base58" pipeline. SHA-256 the compressed pubkey, RIPEMD-160 that digest (= Hash160), prepend the mainnet version byte 0x00, compute a 4-byte checksum as the first 4 bytes of double-SHA-256 of the versioned payload, append it, and Base58-encode.

Note — testnet
Mainnet P2PKH uses version byte 0x00 (addresses start with 1). Testnet uses 0x6f (addresses start with m/n). The code hard-codes 0x00; switching networks today means editing that literal. .codex/commands/validate.md Layer 3 documents both bytes.
Watch out — magic numbers
The version byte 0x00 here and the fee 0.0001 in the send method are exactly the "magic numbers" the Phase 1 gate (CLAUDE.md §10) wants extracted to named constants. They are still inline.
Balance & transaction RPC methods bitcoin_wallet.py:106-145

Four thin RPC wrappers, each guarded by try/except JSONRPCException:

get_balance()listunspent(0, 9999999, [address])sum of UTXO amounts (Decimal)prints error, returns 0

Watch out — errors are printed, not raised
These methods swallow the RPC exception, print() it, and return a sentinel (0/None). That conflicts with the error-handling rule in CLAUDE.md ("never swallow exceptions silently"). It is acceptable for the demo but is on the hardening list. Callers must check for None.
High-level send bitcoin_wallet.py:147-182

create_and_send_transaction(recipient, amount) is the orchestrator: it lists UTXOs, greedily accumulates inputs until their total meets amount, raises ValueError on insufficient funds, computes change as total - amount - 0.0001 (the flat fee), adds a change output back to its own address if positive, then runs create → sign → broadcast, printing the txid on success.

Watch out — coin selection & float math
Selection is naive first-fit (no fee-aware coin selection — that is a Phase 2 goal). The fee is a flat 0.0001 BTC regardless of tx size, and the arithmetic mixes float with the Decimal amounts Bitcoin Core returns, which can raise a TypeError or introduce rounding error. Real wallets do this math in integer satoshis.
The __main__ demo bitcoin_wallet.py:185-199

Running the file directly instantiates a wallet (fresh random key), prints the address and balance, then attempts to send 0.009 BTC to a placeholder recipient string and catches ValueError.

Note
The recipient is the literal 'recipient_btc_address_here' — the demo will fail at createrawtransaction if it ever has funds. It is a smoke-test scaffold, not a usable CLI. Edit those two lines to actually send.

Key concept — Hash160
Bitcoin's address pipeline uses Hash160 = RIPEMD160(SHA256(x)) to shrink a 33-byte pubkey to a 20-byte fingerprint, and a 4-byte double-SHA256 checksum so a typo'd address fails Base58Check decoding instead of silently sending to a black hole. Both appear in the master plan's cross-phase primitives table.

Key logic — the crypto pipeline

The full key-to-address derivation in plain language, then mapped to code.

  1. Entropy → private key. SHA-256 over mixed CSPRNG bytes → 256-bit hex. bitcoin_wallet.py:62
  2. Private key → public key. ECDSA point multiplication K = k·G on secp256k1; compress to 02/03 || x. bitcoin_wallet.py:68
  3. Public key → Hash160. RIPEMD160(SHA256(pubkey)). bitcoin_wallet.py:98
  4. Version + checksum. Prepend 0x00; checksum = first 4 bytes of SHA256(SHA256(version||h160)). bitcoin_wallet.py:100
  5. Base58Check. base58.b58encode(version || h160 || checksum) → the address. bitcoin_wallet.py:103
Note — formula reference
docs/BLOCKCHAIN_MASTER_PLAN.md §7 (Cross-Phase Concerns) and README.md both diagram this same pipeline. The validate command (.codex/commands/validate.md) defines per-layer acceptance: 256-bit key in curve range, correct compression parity, Hash160 ordering, and known-address test vectors (e.g. the genesis address 1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa).

How to run it

There is no Docker and no service launcher — it is a script. The claude-teams.* files are agent launchers, not app launchers.

Address-only (no node needed)

  1. Install deps (not declared in the manifest yet): uv add ecdsa base58 python-bitcoinrpc (or pip install ecdsa base58 python-bitcoinrpc).
  2. From the repo root, generate a key/address in a REPL using the static methods on bitcoin_wallet.py — no node required.

Full demo (node required)

  1. Start Bitcoin Core with RPC enabled (see Configuration) and matching credentials in rpc_credentials.json.
  2. Run the module: python bitcoin_wallet.py (the docs say cd blockchain_dev/bitcoin_wallet_dev first — ignore; the file is at the repo root).
  3. It prints the wallet address and balance, then attempts the placeholder send (which fails until you edit the recipient/amount in the __main__ block).
Note — claude-teams launchers
claude-teams.sh / claude-teams.bat set CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 and launch the Claude Code CLI. They are dev-environment helpers, not ways to run the wallet. This project has no run_blockchain.sh/Docker launcher because there is no long-running service yet (Docker is deferred to Phase 2+ per CLAUDE.md §2).

How to edit & extend it

Practical, owner-facing: where each kind of change lands and the conventions to respect.

Finish hardening Phase 1

The closest-to-hand work, all in bitcoin_wallet.py:

  • Named constants: create a constants.py (per the "one concept per file" rule) for MAINNET_VERSION_BYTE = b'\x00' and DEFAULT_FEE_BTC = Decimal('0.0001'); import them instead of the inline literals at lines 100 and 162.
  • Docstrings: add a one-line docstring to each method (the gate wants them; comments currently stand in).
  • Curve-range check: in generate_private_key, reject keys outside [1, n-1] for secp256k1.
  • Integer-satoshi math: rework create_and_send_transaction to avoid mixing float and Decimal (the fee/change arithmetic).

Add a test suite (the biggest gap)

  1. Create tests/ mirroring the module; add pytest/pytest-cov to the manifest.
  2. Test the three deterministic crypto methods with known vectors — exact equality, never mock the crypto (rule: CLAUDE.md §3 Testing). Validate generate_address against a published address like the genesis address.
  3. Mock the RPC (the external dependency) for get_balance and the tx methods — patch AuthServiceProxy.
  4. Wire tests into CI by extending .github/workflows/ci.yml (today it only runs ruff check).

Move toward the planned Phase 2 layout

The master plan (docs/BLOCKCHAIN_MASTER_PLAN.md §5) sketches a src/ package split (keys/, address/, wallet/, transaction/, rpc/). When you outgrow the single file, follow that structure and the "one class per file" rule. New crypto goes through audited libraries only — no hand-rolled algorithms.

Do not — read-only reference
If you ever clone the Bitcoin Core reference into blockchain_dev/bitcoin_blockchain_dev/, never edit it. The pre-tool-use hook (scripts/hooks/pre-tool-use.cjs) blocks AI writes to any path containing /bitcoin_blockchain_dev/, and the phase-awareness skill blocks it too.
Tip — let the agent guards help you
The post-tool-use hook (scripts/hooks/post-tool-use.cjs) injects a reminder whenever you edit a file whose path contains wallet/keys/address/transaction/signer — it re-lists the crypto-safety checklist. Use .codex/commands/validate.md to run the per-layer crypto validation before you trust a change.

After any change — docs & versioning

Per CLAUDE.md §8/§9: update docs/status.md and add a computed-next-version entry to docs/versions.md. The Stop hook (scripts/hooks/stop.cjs) nudges you if source changed but docs/ did not. Do not hand-edit the version in pyproject.toml — the release workflow bumps it.

Testing

Intended framework is pytest + pytest-cov with a 100% target. Status: not started.

Watch out — no tests exist
There is no tests/ directory, no test file, and no pytest config in pyproject.toml. The Phase 1 completion gate explicitly requires a suite with known Bitcoin test vectors; this is the most significant unmet gate item.

The rules the future suite must follow

Validate against known vectors
Key→pubkey and pubkey→address must match published Bitcoin/secp256k1 test cases (e.g. the genesis address), per .codex/commands/validate.md.
Never mock crypto
Cryptographic operations are deterministic — test them against real computations with exact equality. Mocking them hides bugs (CLAUDE.md §3).
Mock the RPC
The Bitcoin Core node is the external dependency — patch AuthServiceProxy so balance/tx tests run without a node.
Exact equality
No tolerance-based comparison; crypto output is bit-exact.

Build, CI & release

CI — lint .github/workflows/ci.yml

Triggers on push/PR to main/staging/dev and manual dispatch. A single lint job on ubuntu-latest sets up uv + Python 3.13 and runs uvx ruff check .. There is no test, coverage, build, or docker stage yet — consistent with there being no tests and no service.

Manually dispatched on main with a bump input (patch/minor/major). It runs uv version --bump, commits the new pyproject.toml (and uv.lock if present), tags vX.Y.Z, and pushes both the commit and the tag.

Domain glossary

The Bitcoin terms a newcomer needs to read this code.

secp256k1
The specific elliptic curve Bitcoin uses for ECDSA. Defines the generator point G and order n; a private key is a scalar k, the public key is the point k·G.
ECDSA
Elliptic Curve Digital Signature Algorithm — the scheme used to prove ownership of a key when spending.
Compressed public key
33-byte pubkey encoded as a parity prefix (02/03) plus the 32-byte x-coordinate, vs. the 65-byte uncompressed (04) form.
Hash160
RIPEMD160(SHA256(x)) — the 20-byte fingerprint at the core of a P2PKH address.
P2PKH
Pay-to-Public-Key-Hash — the classic Bitcoin address type whose addresses start with 1 on mainnet.
Base58Check
Base58 encoding plus a 4-byte double-SHA256 checksum, so typos are caught on decode.
UTXO
Unspent Transaction Output — the "coins" a wallet owns; balance is the sum of UTXOs for an address.
Raw transaction
The serialized (unsigned or signed) transaction bytes, hex-encoded, as produced by createrawtransaction.
DER encoding
The canonical binary encoding Bitcoin requires for ECDSA signatures.
Change output
The leftover value returned to the sender when inputs exceed amount + fee.
JSON-RPC
The HTTP-based remote procedure protocol Bitcoin Core exposes for wallet/chain operations.
HD wallet (Phase 2)
Hierarchical-Deterministic wallet (BIP-32) — many keys derived deterministically from one seed.
